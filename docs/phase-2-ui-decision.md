# Phase 2 scene and interaction decision

Build a **fixed, interactive factory digital twin** for the six-job scenario. The app opens directly on a three-column, nine-machine scene. Use a consistent workstation component for each stage, with stage-specific details, realistic materials and lighting, machine labels, conveyors, and a visible input-to-output flow. A fixed angled camera with limited orbit and zoom keeps the layout readable. Machine positions come from `six-job-scenario.json`; `[x, z]` values are scene units, not physical measurements.

The primary interaction is selecting a machine. A side panel displays its ID, stage, current state, current operation if any, and affected jobs. The demo failure control appears for `F1`. The machine's visual state uses both color and a label or symbol: idle, processing, failed, or blocked. A blocked machine is healthy but unable to start its next assigned operation because that job is held by the failure; blocked jobs are also shown explicitly. The factory state object, rather than the 3D component, supplies these states.

The production-line viewport has three presentation states: **overview** shows all nine machines; **inspection** zooms to the selected machine while the side panel shows its details; **failure impact** keeps the selected machine in focus and highlights affected jobs and blocked downstream work. Selection does not change the simulation clock. Provide wheel/pinch or explicit zoom controls, drag-to-pan, Fit, and an expanded viewport. Fit or Escape returns to overview. The camera moves in response to selection; it does not constantly orbit during inspection.

Keep the original page structure: the factory and inspector sit above a **production schedule**. The schedule has one row per machine, an integer-minute time axis, and operation bars from `baseline-schedule.json`. Selecting a bar focuses its machine. At failure, the baseline remains visible as the original plan; mark the minute-6 failure line and operations that can no longer proceed. Do not show a replacement schedule until the optimizer returns one.

For this 24-hour demo, the factory layout and 3D assets are authored in advance. A component palette, drag-and-drop editing, and automatic reconstruction from phone photos are outside Phase 2. Keep the workstation renderer able to load a `.glb` asset later without changing machine IDs, positions, or scheduling data. The scene is a digital twin of the **simulated production process**; it is not presented as a measured reconstruction of a real facility.

The state boundary is `factory-state.schema.json`. Phase 2 may load `failure-state.json` through a local adapter. Later the same shape can come from FastAPI. The UI renders the returned schedule and state rather than maintaining a separate clock or machine assignment model in the 3D scene.
